# ADR 0015: One identity per human, players without personal data, Excel import

- Status: Accepted
- Date: 2026-10-16

## Context

The club's business partner asked whether players can exist without personal data, and
wants everything hung off one digital identity that can then be related to users, roles,
groups, persons, players and staff, each with its own attributes. He also wants to bring
players and teams in from Excel.

What exists already (ADR 0002, 0003): `persons` is the one record for any human the club
deals with and needs no login; a `users` row (a login) links to at most one person;
`role_assignments` belong to users; teams, classes and staff assignments point at persons.
So the identity model is mostly there. The gaps were: a person always required a real
`fullName`, there was no stable non-personal handle for a person, and "player" was implied
by a roster row instead of being a profile with its own attributes.

## Decision

**`persons` is the identity.** No parallel `identities` table: every module already points
at `persons`, and a second root would need a join everywhere and a migration of every
foreign key for no gain. Facets hang off it:

| Facet | Where | Attributes |
| --- | --- | --- |
| Player | `players` (one row per person, new) | position, preferred foot |
| Team membership | `team_members`, `class_members` | shirt number, join and leave dates |
| Staff | `staff_assignments` | function, employer, gabinete, team or class |
| Login | `users.person_id` | email, password; roles in `role_assignments` |
| Guardian, member (sócio) | `guardianships`, `memberships` | relationship; member number |

A facet exists or not independently: a coach who also plays veterans has a `players` row
and a staff assignment on the same person; a player with no login has no `users` row.
`GET /api/people/:id/identity` returns the facets of one person (general tier only).

**New columns on `persons`** (both `general` tier):
- `identity_code`: `RSC-` plus 8 hex characters, generated by the database, unique. It is
  the non-personal handle for rosters, spreadsheets and bug reports. It is not a secret and
  grants nothing.
- `is_pseudonymous`: true when `full_name` is an alias, not a real name.

**Players without personal data**: a player can be created from an alias alone
("Jogador 9"): `full_name` holds the alias, `display_name` too, every personal-tier column
(birth date, contacts, federation number) stays null, and `is_pseudonymous` is true. They
can be on teams, evaluated and called up like anyone else. When a real name arrives (edit
the person, or an import row with the same code), the flag clears and the identity code
stays, so history is kept. We did not make `full_name` nullable: a dozen modules print it
and an alias keeps them all working.

**Privacy tiers (ADR 0003) are unchanged.** The new columns are general tier. Importing
sporting data needs `people.write` (players) or `teams.write` (teams), which are club-wide
only. Health data still never touches these tables. Erasure still deletes the person and
the `players` row cascades.

**Excel import** (`/api/imports/:kind/{template,preview,apply}`, kind `players` or
`teams`), screen under Mais › Importar:
- `.xlsx` only, 5 MB and 2000 rows at most, sent as the raw body (as documents are). First
  sheet, first row is the header; headers are matched ignoring case and accents, in
  Portuguese or English.
- A downloadable template per kind holds the headers and an instructions sheet.
- Preview runs the same code as apply inside a transaction that is rolled back, so it
  reports exactly what apply would do. Each row runs in a savepoint: a bad row is reported
  with a machine-readable reason (translated in the app) and skipped; the rest are applied.
- Players: a row needs a name or an alias. Matching order: identity code (unknown code is
  an error), federation number, name plus birth date, alias for pseudonymous players.
  Existing values are only filled in, never overwritten or blanked. A named row matching a
  pseudonymous player claims it. The team column resolves a team of the current season by
  name; the shirt number needs a team. Every imported person gets a `players` row.
- Teams: season is always the current one; organisation defaults to the club; age group is
  matched by name (and category when two share a name); category defaults to mixed.
- Reports contain names, aliases and codes of rows, never other personal data. The
  existing CSV importer (`pnpm people:import`) stays for the club's historical sheets.

## Alternatives considered

- **A separate `identities` root table with person, player, staff, user as subtypes.**
  Cleaner on paper, but it would move every foreign key of ~20 modules and add a join to
  every read. The facet tables already give the same shape.
- **Nullable `full_name`.** Honest, but every list, roster and export would need a
  fallback; an alias in the same column does it once.
- **A generic `attributes` JSON column per facet.** Flexible, but untyped and invisible to
  the tier checks. Facet-specific attributes are real columns instead.
- **Reading `.xls`/CSV too, or SheetJS.** The club uses Excel; `exceljs` reads and writes
  `.xlsx` and is maintained. CSV stays on the CLI.

## Consequences

- New facets (referee, volunteer) are a new table pointing at `persons`, not a new root.
- Re-importing a sheet of pseudonymous players without codes matches by alias only; two
  players with the same alias are reported as ambiguous. Give them codes, or distinct
  aliases.
- Follow-ups not done: exporting current players with their codes to Excel (so edits can be
  re-imported by code), importing staff and guardians from Excel, and showing the code and
  facets on the person screen.
